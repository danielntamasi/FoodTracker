# FoodTracker

iOS calorie and macro tracking app. Users add food entries via photo (AI vision), barcode scanning, or manual input. The app shows daily summaries, macro breakdowns, and history.

## Tech Stack

- **Language:** Swift, SwiftUI
- **Data:** SwiftData (single `FoodEntry` model)
- **Min Target:** iOS 17+ (SwiftData requirement)
- **Build:** Xcode project (no SPM dependencies)
- **No tests** currently
- **Orientation:** Portrait only (locked)

## Architecture Notes

- **Design system:** `DesignSystem.swift` provides centralized design tokens via the `DS` enum. Sub-enums: `DS.Color` (backgroundPrimary/Secondary/Elevated/Subtle, textPrimary/Secondary/Tertiary, protein/carbs/fat, success/danger, border/borderStrong, ringTrack/overlayText/dimming/shadowColor/heroTextShadow/iconThumbnailBg), `DS.Spacing` (xs/s/m/l/xl/xxl/screenEdge), `DS.Radius` (s/m/l/xl), `DS.Typography` (displayL/displayM/numberL/numberM/labelL/labelM/labelS/caption), `DS.Gradient` (calorieRing/cardShimmer/heroGlow/plusButton). All `DS.Color` tokens are **adaptive** (light/dark) via `UIColor { traitCollection in }` wrapped in `Color(uiColor:)`. Private helpers `adaptive(light:dark:)` (hex-based) and `adaptiveOpacity(lightBase:lightAlpha:darkBase:darkAlpha:)` (opacity-based). Includes `Color(hex:)` initializer, `AppCardModifier` (`.appCard()` ViewModifier for consistent card styling), and reusable components: `CalorieRing` (animated gradient ring with glow, center content for consumed/goal/remaining), `MacroArc` (compact 64pt circular progress per macro with over-goal danger state), `MacroPill` (capsule chip with value + unit letter on colored background). **Appearance mode:** `AppearanceMode` enum (in `FoodTrackerApp.swift`) with `.system`/`.light`/`.dark` cases, stored in `sharedDefaults` via key `AppConstants.Defaults.appearanceMode`. `FoodTrackerApp` uses `@AppStorage` to drive `.preferredColorScheme()` reactively — defaults to `.system` (follows device setting). User toggle in SettingsView "APPEARANCE" section (segmented picker). Global tint `DS.Color.protein` on root view. All views use DS tokens for colors, typography, spacing, and radii — no raw system colors.
- **Single model:** `FoodEntry` is the only SwiftData model. Fields: `id`, `name`, `calories` (per-serving), `proteinGrams` (per-serving), `carbsGrams` (per-serving), `fatGrams` (per-serving), `servings` (Double, default 1.0), `servingDescription` (String?, e.g. "1 medium"), `servingGrams` (Double?, weight of one serving), `date`, `photoData`, `mealGroupID`, `mealName`, `notes`, `iconName`, `sortOrder`, `barcode` (String?, barcode string from OFF scan), `isGeneratedImage` (Bool, default false — distinguishes AI-generated images from real photos). Computed properties `totalCalories`, `totalProteinGrams`, `totalCarbsGrams`, `totalFatGrams` multiply per-serving values by `servings`. All display/aggregation uses `total*`; editing operates on per-serving values. Existing entries auto-migrate via SwiftData defaults (`servings = 1.0`, serving info fields `nil`). Meal grouping uses `mealGroupID` (shared UUID) + `mealName` fields, not relationships.
- **App Group:** `group.com.DNT.foodtracker` shared between main app and widget. `SharedConfig.swift` provides `appGroupID`, `sharedModelContainer`, and `Double.roundedTo(_:)` (in SharedConfig so both main app and widget targets can use it). `SharedHelpers.swift` provides `sharedDefaults` (UserDefaults suite). All UserDefaults access uses `sharedDefaults` (except `VisionProvider.selected` which uses `.standard`). `DailyTarget` reads/writes directly to `sharedDefaults`, so the widget sees target changes immediately. `FoodTrackerApp.init()` migrates legacy UserDefaults on first launch.
- **`foodIconName()`:** Free function in `FoodEntry.swift` that maps food names to SF Symbol icons via keyword matching. Mappings are a file-level `let` (not rebuilt per call).
- **Shared helpers:** `SharedHelpers.swift` contains pure utility functions: `formatServings()` (fraction characters), `formatMacro()`, macro calorie functions (`proteinCalories()`, `carbCalories()`, `fatCalories()`, `totalMacroCalories()`, `macroPercentages()`), `dominantColor(from:colorScheme:)` (CIAreaAverage extraction — dark mode darkens, light mode blends toward white for soft pastels), `iconHeroColor(for:)` (adaptive hero background colors — dark low-range, light pastel-range via `UIColor { traits in }`), `quickAddEntry/quickAddMealGroup` (ModelContext helpers — copy serving info fields), `DailyTarget.hasTargets`, `perServingFromPer100g()` (shared per-100g → per-serving conversion used by `PhotoAnalysisView` and `FoodAnalysisPipeline`), `String.titleCased()` extension. `SharedViews.swift` contains shared SwiftUI view components (`MetricPill`, `HeroMacroDonut`, `DailyGoalBarsView`, `ServingPicker`, `USDAResultCard`, `USDAResultsList`, `CachedThumbnailImage`). `USDAResultCard` displays a single USDA result with description, serving info, calories, colored macros, and a selected-state checkmark. `USDAResultsList` takes `[USDALookupResult]` and a selection binding, showing cards in a vertical stack with tap-to-select/deselect. `ServingPicker` is a `.wheel`-style `Picker` showing ¼-increment values (0.25–20+), used by `AddEntryView`, `EditEntryView`, and `PhotoAnalysisView`. `HeroPhotoSection.swift` contains the shared immersive hero layout (photo with gradient or icon-based gradient) used by `EditEntryView` and `MealSummaryView`.
- **Vision pipeline:** `FoodAnalysisPipeline.analyzeImage()` → vision provider identifies foods → USDA/FNDDS looks up macros (falls back to AI estimates). `IdentifiedFood.calories/proteinGrams/carbsGrams/fatGrams` always represent the TOTAL for the vision-detected portion; `IdentifiedFood.servings` stores how many servings that equals. Pipeline scales USDA per-100g values by `portion_grams / 100` (not `servingGrams / 100`) so displayed values match the actual portion. AI estimate fallback similarly scales by `portion_grams / servingGrams`. Hidden calories from vision (oils, butter, sauces) are added to USDA-derived calorie totals and distributed to fat macro. Enhanced sanity checking via `sanitizeNutrition()`: (1) derive calories from macros when zero, (2) correct calories >25% divergent from macro-derived value, (3) physics-based cap (`calories > portionGrams * 9` is impossible). `sanitizeNutritionWithTrace()` variant returns `[String]` of heuristics that fired. `NutritionSource` enum includes `.label`, `.estimate`, `.barcode`, and `.usda`. `FoodAnalysisPipeline.estimateNutrition(for:)` provides text-based AI nutrition estimation. `FoodAnalysisPipeline.analyzeImages(_:)` supports multi-angle precision mode (2-3 photos). Trace-collecting variants (`analyzeImageWithTrace`, `analyzeImagesWithTrace`, `processVisionResponseWithTrace`) return a `PipelineTrace` alongside results for debugging. Results from TaskGroup are sorted by original insertion index for deterministic ordering. `VisionAPIService` handles both providers with `identifyFoods(in:plateSize:)`, `identifyFoods(images:plateSize:)` (multi-angle), `identifyFoodsWithRawText` (trace variants returning raw API response text + prompt), and `estimateNutrition(for:)` methods. Vision prompt functions (`visionPrompt`, `multiAngleVisionPrompt`) are module-internal. Vision prompt uses chain-of-thought reasoning: step-by-step plate reference, volume estimation, cooking method analysis, hidden calorie detection (oils, sauces, butter), and confidence scoring (1-5). Response JSON includes `hidden_calories_estimate`, `hidden_calories_source`, `confidence`, and `cooking_method` fields. `IdentifiedFood` carries corresponding `hiddenCaloriesEstimate`, `hiddenCaloriesSource`, `confidenceScore`, `cookingMethod` fields. Pipeline accepts optional `cookingMethod: CookingMethod?` and `plateSize: PlateSize` parameters. Types include `CookingMethod` enum (raw/grilled/fried/baked/steamed/sauteed/roasted/boiled/airFried/other with `usdaQueryTerm` and `iconName`) and `PlateSize` enum (small ~8"/medium ~10"/large ~12" with `portionScale` using area-based scaling `pow(diameter/10.5, 2)` relative to standard 10.5" plate). `FoodAnalysisPipeline` in `FoodAnalysisPipeline.swift` contains `analyzeImage()`, `analyzeImages()`, `estimateNutrition()`, `sanitizeNutrition()`. JSON parsing (`decodeVisionResponse()`, `extractJSON()`) are file-level functions.
- **Two vision providers:** Claude Sonnet 4.6 and Gemini 2.0 Flash, selectable in Settings. Provider config (including keychain accounts) lives in `VisionProvider` enum (`VisionProvider.selected` uses `UserDefaults.standard`, not `sharedDefaults`). Single unified service actor: `VisionAPIService`. Both providers send API keys via HTTP headers (not URL query params): Claude uses `x-api-key`, Gemini uses `x-goog-api-key`.
- **USDA service:** `USDAService` actor uses a user-provided API key from Keychain (account: `AppConstants.Keychain.usdaAPIKey`), falling back to `DEMO_KEY` if none set. API key is cached in-memory; call `invalidateAPIKeyCache()` after saving a new key in Settings. Free keys available at fdc.nal.usda.gov/api-key-signup (1,000 req/hr vs 30/hr). `USDALookupResult` conforms to `Identifiable` (UUID). Primary method `lookupFoodOptions(for:cookingMethod:) -> [USDALookupResult]` returns up to 5 scored/de-duped results using a **two-pass cooking method strategy**: tries query with cooking method first, falls back to stripped query. `lookupFood(for:cookingMethod:)` is a thin wrapper returning `.first`. `lookupPreparedFood(for:cookingMethod:)` queries the FNDDS (Survey) database which has 5,624 prepared food entries with recipe-level nutrition — used for cooked/prepared foods. Both FDC and FNDDS lookups share `executeUSDASearch()`. Scoring: penalizes processed forms, prefers "raw" only if query mentions it, +3 for full query word match, +2 for energy data, +5 for matching cooking method, -3 for mismatched cooking method. `buildResult()` derives calories from macros when missing. Query cleaning: strips parenthetical content, then removes cooking methods (18 actual cooking verb terms in `cookingMethods` static set — descriptors like "creamy", "crispy", "seasoned" are preserved since they affect nutrition). Trace-returning variants (`lookupFoodWithTrace`, `lookupFoodOptionsWithTrace`, `lookupPreparedFoodWithTrace`) return `[PipelineTrace.USDAQueryTrace]` alongside results for debugging. Each result includes serving info extracted from `foodMeasures` → `servingSize` → detail endpoint `foodPortions` (3-tier fallback). Pipeline tries FNDDS first for cooked foods, falls back to FDC.
- **Barcode flow:** `BarcodeScannerView` → `OpenFoodFactsService` → presents results in `PhotoAnalysisView(foods:)`. Barcode items include per-100g nutrition data and serving size, enabling portion selection in the review screen. `IdentifiedFood` carries optional `caloriesPer100g`, `proteinPer100g`, `carbsPer100g`, `fatPer100g`, `servingGrams`, `servings`, and `barcode` fields for this purpose. `OpenFoodFactsService.Product` also includes per-100g fields. Barcode string is threaded from scan → `IdentifiedFood.barcode` → `FoodEntry.barcode` for correction tracking.
- **OFF community corrections:** When a user scans a barcode product and manually edits the macro values (beyond rounding tolerance), the app detects the correction in `PhotoAnalysisView.saveAll()` or `EditEntryView.finishEditing()` and prompts to submit it back to OpenFoodFacts via `OpenFoodFactsService.submitCorrection()`. OFF credentials (username/password) stored in Keychain (accounts: `off-user-id`, `off-password`), entered via Settings. Per-device `app_uuid` stored in `UserDefaults.standard` key `off-device-uuid`. If no credentials configured, corrections are silently skipped. Fire-and-forget: errors logged via `os.Logger` (non-2xx at `.warning`, failures at `.error`), never thrown. Servings-only changes don't trigger corrections.
- **Photo flow:** `PhotoCaptureView` → captures image → `PhotoAnalysisView(image:)` → runs `FoodAnalysisPipeline`. `PhotoUploadView` → photo library picker → same `PhotoAnalysisView` flow. Both use `ImagePicker(sourceType:)` which accepts `.camera` (default, falls back to `.photoLibrary` on Simulator) or `.photoLibrary`. **Precision mode:** `PrecisionPhotoCaptureView` captures 2-3 photos from different angles (top-down + side), then sends all to `FoodAnalysisPipeline.analyzeImages()` via `MultiAngleAnalysisView`. Accessible via "Precision" in the radial menu (`QuickAddAction.precisionPhoto`).
- **Pipeline trace & bug reports:** `PipelineTrace` (Codable struct in `PipelineTrace.swift`) captures full pipeline state: vision provider, raw API response text, parsed foods, per-food USDA query traces (queries attempted, results, selected match), AI fallback data, sanitization before/after snapshots with heuristic names. Conversion helpers (`traceVisionItem`, `traceUSDAResult`, `traceAIEstimate`, `traceIdentifiedFood`) bridge internal types to trace structs. `BugReportService` (enum in `BugReportService.swift`) takes a `ReportContext` (trace, photos, complaint, foods, optional correction values) and generates a zip via `NSFileCoordinator(.forUploading)` containing `report.md` (structured markdown with tables for Claude Code ingestion), `pipeline_trace.json` (full Codable trace), and photo JPEGs. `BugReportView` (in `BugReportView.swift`) presents a summary sheet with photo preview, pipeline config, identified foods, free-text complaint field, and Export button triggering `UIActivityViewController` via `ShareSheet` wrapper. "Report an Issue" button appears in `PhotoAnalysisView` (below results list, when trace exists) and `EditEntryView` (below timestamp in read mode, with original vs corrected values). `PhotoAnalysisView.analyzePhoto()` uses `analyzeImageWithTrace` to collect traces; `reEstimateWithContext()` uses `processVisionResponseWithTrace` to update traces on re-estimation. `MultiAngleAnalysisView` passes trace to `PhotoAnalysisView` via `init(image:prefilled:trace:)`.
- **Accuracy tracker:** `AccuracyTracker` (actor in `AccuracyTracker.swift`) records user corrections to AI-estimated nutrition values. Tracks original vs corrected calories/macros per food entry. Provides `AccuracySummary` with total corrections, average calorie error, systematic bias direction (underestimates/overestimates/balanced), and most-corrected food types. Corrections recorded from `EditEntryView.finishEditing()` when nutrition values change. `AccuracyDetailView` (in `SettingsView.swift`) shows correction history, accuracy stats, and most-corrected foods under Settings > Estimation Accuracy. Data persisted as JSON file in documents directory.
- **PhotoAnalysisView dual init:** `init(image:)` for photo analysis, `init(foods:)` for barcode/pre-resolved results. Barcode/label items with per-100g data get a `portionPicker` (uses shared `ServingPicker` wheel); `applyServings()` recalculates all macros from per-100g base values. For photo analysis, shows a "Preparation Context" section with: (1) **Cooking method picker** — horizontal scrolling pills (Auto + all `CookingMethod` cases) pre-selected from AI-detected method, changing triggers `reEstimateWithContext()` re-analysis; (2) **Plate size picker** — segmented control (Small ~8"/Medium ~10"/Large ~12"), changing also triggers re-estimation. **Confidence badges** shown per food item (green High 4-5, yellow Medium 3, red Low 1-2) via `confidenceBadge(score:)`. Low-confidence ingredients get a red border highlight. **Hidden calorie info** shown when `hiddenCaloriesEstimate > 0` with eye.slash icon and source description. `saveAll()` stores the photo thumbnail only on the first entry of each meal group to avoid duplicate blob storage, and passes `servingDescription`/`servingGrams` from `IdentifiedFood` to `FoodEntry`; `FoodEntryRow` accepts an optional `groupPhotoData` parameter so expanded sub-items inherit the group's photo for display.
- **Custom tab bar:** `ContentView` uses a `ZStack` with a floating `HStack` tab bar (`.ultraThinMaterial`, `RoundedRectangle(cornerRadius: 24)`) instead of stock `TabView`. Center "+" button toggles a radial arch menu overlay with 7 options (Recent, Search, Build, Photo, Precision, Upload, Barcode) that fan out in an arc above the button with staggered spring animations. Items are placed via `.overlay` on the + button (so they animate outward from it) with horizontal correction via `layoutWidth` GeometryReader so they land centered on screen despite the button being offset in the HStack. Uses `AppTab` enum for tab state, `QuickAddAction` enum (`.photo`, `.barcode`, `.search`, `.browse`, `.uploadPhoto`, `.buildMeal`, `.precisionPhoto`) for action routing. "Search" opens `SearchFoodView`; "Build" opens `BuildMealView`; `AddEntryView` is opened from within `SearchFoodView` for manual/prefilled entry. Plus button rotates 45° (becomes X) when menu is open. Dimming backdrop dismisses on tap. `ScaleButtonStyle` provides press animation for the "+" button. Add-entry sheets live in `ContentView`, not `DailySummaryView`.
- **SearchFoodView:** (in `SearchFoodView.swift`) Unified search entry point opened from "Search" in the radial menu. Search bar at top with debounced (500ms) input. Shows sections: **Recent Foods** (matches from user's `FoodEntry` history with `FoodIconThumbnail`, serving description, de-duped by name, most recent first, tapping creates a quick-add copy), **USDA Database** (results from `lookupFoodOptions` with staggered spring animations on appearance, tapping opens `AddEntryView` pre-filled; skeleton shimmer loading placeholders while searching), **AI Estimate** (purple-accented button triggers `FoodAnalysisPipeline.estimateNutrition()`; result shown with sparkles icon and purple calorie text), and **Manual Entry** (always-visible row with chevron). Empty/error state uses pulsing magnifyingglass `symbolEffect`. Extracted subviews: `SearchSkeletonRows`, `USDAResultButton`, `AIEstimateCard`, `SearchEmptyState`. USDA/AI results use `.sheet(item: $prefillResult)` (requires `USDALookupResult: Identifiable`); manual entry uses separate `.sheet(isPresented:)`. All paths dismiss SearchFoodView after saving via `AddEntryView(onSave:)` callback. `AddEntryView` accepts optional `prefill: USDALookupResult?`, `onSave: (() -> Void)?`, and `onIngredientAdded: ((IngredientItem) -> Void)?` parameters.
- **Build meal:** `BuildMealView` (in `BuildMealView.swift`) lets users compose a named meal from multiple ingredients. "Add Ingredient" is a `Menu` offering all input methods: Search, Recent Foods, Take Photo, Upload Photo, Scan Barcode, and Enter Manually. Each opens the corresponding view with an `onIngredientAdded`/`onIngredientsAdded` callback so items are returned as `IngredientItem`s instead of saving to SwiftData. Running totals (calories + colored macros) shown in the footer. Swipe-to-delete on ingredients. On save, creates `FoodEntry` instances for each ingredient sharing a `mealGroupID` and `mealName`, following the existing meal group pattern. `IngredientItem` struct (in `BuildMealView.swift`) holds per-ingredient data (name, calories, macros, servings, serving info). `IngredientSource` enum drives sheet presentation. Accessed via "Build" in the radial menu. Views supporting ingredient mode via callbacks: `SearchFoodView`, `BrowseFoodsView`, `PhotoAnalysisView`, `PhotoCaptureView`, `PhotoUploadView`, `BarcodeScannerView`.
- **Browse foods:** `BrowseFoodsView` (in `BrowseFoodsView.swift`) shows Favorites (starred foods and meals), top 5 frequent foods (by all-time add count, dynamically ranked), up to 5 recent meals (de-duplicated by meal name, tapping re-adds all ingredients via `quickAddMealGroup`), and 10 recent unique foods from previous days. Tapping a food creates a new `FoodEntry` with `servings: 1.0` explicitly set, copying `servingDescription`/`servingGrams` from the source entry. Accessed via "Recent" in the radial menu. Favorites section uses `FavoriteItem` enum (`.food`/`.meal` cases) to render both individual foods and meal groups.
- **Favorites:** `FavoriteFoods` enum (in `SharedHelpers.swift`) manages a `Set<String>` of lowercase food/meal names stored in `sharedDefaults` (key: `AppConstants.Defaults.favoriteFoodNames`). `isFavorite(_:)` checks membership, `toggle(_:)` adds/removes and returns new state. Star button appears in `EditEntryView` (floating capsule, read mode) and `MealSummaryView` (top-left capsule) — filled star (`star.fill`, `DS.Color.carbs`) when favorited, hollow star when not. `BrowseFoodsView` shows a "Favorites" section at the top with both individual foods and meals via the `FavoriteItem` enum.
- **DailySummaryView layout:** Uses `List` with `.listStyle(.plain)` and `.scrollContentBackground(.hidden)` for card-style layout with native swipe actions. Summary card wrapped in glassmorphic background (`secondarySystemGroupedBackground`, cornerRadius 16, subtle shadow). Food entries in individual cards (cornerRadius 12). Time-of-day section headers have tinted icon circles. Custom empty state with `symbolEffect(.pulse)`. Swipe actions (all trailing): delete (red, destructive), edit (blue), add-again (green). Cross-section drag-to-reorder via `FlatListItem` enum (`.sectionHeader`, `.entry`, `.expandedSubItem`) flattened into a single `ForEach` with `.onMove`; section headers and expanded sub-items are `.moveDisabled(true)`. `moveItems(from:to:)` walks the reordered flat list to find each entry's nearest preceding section header; if section changed, `adjustedDate(for:movingTo:)` updates the entry's hour (Morning→9, Afternoon→13, Evening→18, preserving day/minute/second). All 3 section headers always shown (empty ones at 50% opacity as drop targets). `assignInitialSortOrders()` ensures all entries have stable sortOrder values. `coloredMacroText()` free function renders colored inline macro text (blue P, orange C, purple F) used by both `FoodEntryRow` and `MealEntryRow`. Animated numbers via `.contentTransition(.numericText())` on calorie counts and macro values in `MacroDonutCard`, `MacroProgressLabel`, and `MacroLabel`. Meal group rows have a chevron button toggling `expandedGroups: Set<UUID>` to show/hide individual entries inline. Tapping a meal group row opens `MealSummaryView` (immersive detail sheet). Widget data synced reactively via `.task(id: widgetSyncID)` whenever totals change, calling `syncWidgetData()` → writes to shared UserDefaults + `WidgetCenter.shared.reloadAllTimelines()`.
- **Serving selector:** `AddEntryView`, `EditEntryView`, and `PhotoAnalysisView` all use the shared `ServingPicker` (`.wheel`-style, ¼ increments, ~3 visible rows). User enters per-serving values; `servings` is persisted on `FoodEntry` and computed `total*` properties handle multiplication. `EditEntryView` loads `entry.servings` on edit and saves it back (no manual multiplication). When serving size info is available (`servingDescription`/`servingGrams`), a non-editable "Serving Size" row is shown above the picker. In `EditEntryView` read mode, serving size is displayed near the timestamp as "N × description (Xg)". Serving info is populated from USDA lookups, barcode scans (OpenFoodFacts), and vision pipeline results.
- **Auto-capitalization:** All food name `TextField`s use `.textInputAutocapitalization(.sentences)` — applies in `AddEntryView`, `EditEntryView`, and `PhotoAnalysisView` (meal names, ingredient names, standalone names).
- **DailySummaryView components:** `FoodEntryRow` (`CachedThumbnailImage` for async-decoded 52×52 thumbnails, colored macros), `MealEntryRow` (same), `MacroLabel`, `MacroDonutCard` (animated numbers, shows "X left/over"), `MacroProgressLabel` (animated numbers + progress bar). Uses `TimeOfDay` enum (with `tintColor`, `startHour`, `defaultHour`) for Morning/Afternoon/Evening sections, `EntryDisplayItem` enum for grouping logic, and `FlatListItem` enum (`.sectionHeader`, `.entry`, `.expandedSubItem`) for the flattened drag-reorder list. `groupedDisplayItems()` free function uses `Dictionary(grouping:)` for O(n) meal group assembly, reused by `HistoryView`. Performance: `totals` computed property does a single-pass reduce for all macros; `entriesByPeriod` buckets entries by time-of-day in one pass (avoids 3x filter). Reverse chronological toggle (arrow button) persisted in `sharedDefaults`. `FoodIconThumbnail` view renders a colored SF Symbol in a rounded rect background (used when no photo); `foodIconColor(for:) -> Color` free function maps icon names to colors. `MealGroup: Identifiable` struct (id, name, entries) used for sheet presentation.
- **MealSummaryView:** (in `MealSummaryView.swift`) Immersive full-screen sheet opened when tapping a meal group (in both `DailySummaryView` and `HistoryView`). Uses `HeroPhotoSection` for the photo/icon hero layout, shows ingredient list, `DailyGoalBarsView` (when targets set), formatted timestamp. Uses shared `dominantColor()` (adaptive) and `iconHeroColor()` (adaptive) from `SharedHelpers.swift`.
- **Widget:** `FoodTrackerWidgetExtension` — `.systemMedium` widget showing donut chart with calories left + macro progress bars. Uses `TimelineProvider` that reads from shared SwiftData store and App Group UserDefaults. Refreshes every 15 min. No-target fallback shows simple large calorie number + P/C/F labels instead of donut. Reads `widgetLastSync` timestamp to zero out values if data is from a previous day (prevents stale display). Widget has its own `W` color enum with the same `adaptive(light:dark:)` helper mirroring `DS.Color` values — auto-adapts to light/dark mode.
- **DailyTarget:** UserDefaults wrapper in `SettingsView.swift` for calorie/macro targets (uses `sharedDefaults`). `DailyTarget.hasTargets` static computed property (in `SharedHelpers.swift`) replaces duplicate checks across views.
- **HistoryView collapsible days:** `expandedDays: Set<String>` controls which date sections are expanded. All days start collapsed by default. Section headers are tappable `Button`s with chevron, calorie count, and `coloredMacroText` for macros.
- **SourceBadge:** View in `PhotoAnalysisView.swift`.
- **HealthKit integration:** `HealthKitService` (singleton actor in `HealthKitService.swift`) syncs food entries to Apple Health as dietary samples (calories, protein, carbs, fat). `syncEntry(_:)` creates 4 `HKQuantitySample` records with `FoodTrackerEntryID` metadata for targeted deletion. `deleteEntry(id:date:)` queries samples by metadata predicate. `updateEntry(_:)` = delete + sync. `isEnabled` static property reads/writes `healthKitSyncEnabled` from `sharedDefaults`. Toggle in Settings requests authorization on enable, reverts if denied. Sync calls are fire-and-forget `Task { await ... }` at all entry creation/update/delete points: `AddEntryView.save()`, `PhotoAnalysisView.saveAll()`, `EditEntryView.finishEditing()`, `BuildMealView.saveMeal()`, `quickAddEntry/quickAddMealGroup` (SharedHelpers), `DailySummaryView` (3 delete sites), `HistoryView` (3 delete sites). **Xcode setup:** HealthKit capability must be added manually in Signing & Capabilities.
- **Image Playground:** `ImagePlaygroundService` (actor in `ImagePlaygroundService.swift`) generates illustrated food images on-device using Apple's Image Playground framework. Uses `ImageCreator` (iOS 18.4+, `#if canImport(ImagePlayground)`) with `.illustration` style. Lazy generation: triggered when `EditEntryView` or `MealSummaryView` opens for an entry with `photoData == nil`. Stores result in existing `photoData` field; `isGeneratedImage` flag on `FoodEntry` distinguishes AI images from real photos. Generated images are cleared on name change (so they regenerate) and not copied on "Add Again" (new entries generate their own). `isAvailable` checks `ImagePlaygroundViewController.isAvailable` (requires Apple Intelligence hardware). `isEnabled` toggle in Settings (defaults ON, hidden on incapable devices). `HeroPhotoSection` shows sparkles animation during generation. App targets iOS 17+; all Image Playground code gated behind `#available`.
- **EditEntryView:** Immersive hero sheet layout using `HeroPhotoSection` — full-bleed photo (65% height) with gradient fade to dominant color (extracted via `CIAreaAverage`), or icon-based gradient hero when no photo. Read mode shows food name, metric pills (via `HeroPhotoSection`), macro donut chart with percentage breakdown, `% of Daily Goal` bars (when targets set), serving size info (when available), formatted timestamp. Floating capsule buttons ("Edit"/"Done"/"Cancel") overlay the hero instead of toolbar. Edit mode replaces hero with custom grouped form sections on `.ultraThinMaterial`-style dark background: FOOD (name with inline lookup icons, calories), USDA RESULTS (multi-result cards via `USDAResultsList` when results available — tapping a card fills macros/serving info), MACROS (protein/carbs/fat — per-serving values), SERVINGS (serving size label when available, `ServingPicker` wheel, total preview), DATE & TIME (`DatePicker` with `.date` + `.hourAndMinute`). USDA lookup uses `lookupFoodOptions()` and barcode scan both persist `servingDescription`/`servingGrams` on the entry. Inline lookup icons (sparkles for USDA multi-result lookup, barcode.viewfinder for scan) appear only when `nameChanged` (entry.name != originalName); `lookupError` shown inline in FOOD section. `finishEditing()` saves `entry.servings = servings` (no manual multiplication — computed `total*` properties handle it). Snapshots original values (including date, servings, and photoData) on edit; Cancel restores all originals, Done title-cases and updates iconName. "Remove Photo" destructive button in edit mode sets `entry.photoData = nil` and clears `extractedColor`; Cancel restores `originalPhotoData`.
- **EditEntryView barcode scan:** `EditBarcodeScannerView` (in `EditEntryView.swift`) is a lightweight barcode scanner that returns `(OpenFoodFactsService.Product, String)` (product + barcode) via a callback, updating the entry's name/calories/macros and storing `entry.barcode` for correction tracking. Uses `BarcodeCameraView` from `BarcodeScannerView.swift`.
- **Title casing:** `String.titleCased()` extension (in `SharedHelpers.swift`) is applied at all entry creation points: `FoodAnalysisPipeline` (vision), `PhotoAnalysisView.saveAll()`, `AddEntryView.save()`, `EditEntryView.finishEditing()`, `OpenFoodFactsService` (barcode). One-time migration in `FoodTrackerApp` fixes historic entries' `name` and `mealName` fields (UserDefaults key: `AppConstants.Defaults.didMigrateNameCasing`).
- **NutritionLookup:** `@Observable` class (in `NutritionLookup.swift`) encapsulating shared USDA/AI lookup state and logic. Properties: `isLookingUp`, `lookupError`, `lookupResults`, `selectedResultIndex`, `isEstimating`, `aiEstimate`. Methods: `lookupNutrition(for:)`, `runAIEstimate(for:)`, `reset()`. Used by `AddEntryView`, `EditEntryView`, and `SearchFoodView` via `@State private var lookup = NutritionLookup()`, replacing 6 duplicated `@State` vars and 3 duplicated methods in each view. UI bindings use `Binding(get:set:)` for `selectedResultIndex` since `@Observable` doesn't support `$` binding syntax.
- **PerformanceCalculator:** Struct (in `PerformanceCalculator.swift`) containing all performance calculation logic extracted from `PerformanceTileView`. Includes: `buildDailyRecords()`, `dotStatus()`, `isDayFullyOnTarget()`, `dayOverallStatus()`, `daysOnTarget()`, `daysWithData()`, `currentStreak()`, `bestStreak()`, `globalCurrentStreak(allEntries:)`, `avgDelta()`, `avgCalories()`, `yearMonthlyDotsFrom()`, `monthDotColor()`, `monthWeeklyDotsFrom()`, `monthTrend()`, `adherenceColor()`. `globalCurrentStreak()` calculates streak across all entries (not period-scoped) by building daily records from the earliest entry to today. Also contains `TrendDirection` and `PerformanceThresholds` enums. `PerformanceTileView` instantiates via computed property and delegates all calculations.
- **AppConstants:** Centralized configuration constants (in `AppConstants.swift`). `AppConstants.API` (model names, image constraints), `AppConstants.Keychain` (account strings for Claude, Gemini, USDA, OFF), `AppConstants.USDA` (nutrient IDs), `AppConstants.Defaults` (UserDefaults keys including `appearanceMode`). Referenced by `VisionAPIService`, `FoodAnalysisModels`, `USDAService`, `OpenFoodFactsService`, `FoodTrackerApp`, `DailySummaryView`, `SettingsView`.
- **Performance tile:** `PerformanceTileView` (in `PerformanceTileView.swift`) shows adherence-focused stats with `PerformancePeriod` enum (week/month/year) segmented picker. "On target" = all macros with targets set are within ±10%; days with no entries are excluded from totals. Week view has two modes toggled by a button in the header (`useBarChart` state, defaults to bar chart): **Bar chart mode** shows a 7-day grouped `BarMark` chart (Swift Charts) with 4 bars per day (Cal gray, Protein blue, Carbs orange, Fat purple) as percentage of daily target, a dashed `RuleMark` at 100%, a subtle green target zone band (90–110%), Y-axis showing percentage, and a legend row below. Uses `MacroBarEntry` struct and `.position(by:)` for side-by-side grouping. Below the chart, a row of small status dots shows `dayOverallStatus`. **Classic mode** shows the original 7×N dot matrix (rows = Cal/Pro/Carb/Fat, columns = days). Toggle icon switches between `chart.bar.fill` and `circle.grid.3x3.fill`. Both modes share the hero stat ("X of Y on target" + adherence %), avg calorie delta, and global current streak footer (calculated across all entries via `globalCurrentStreak()`, not limited to the selected period). `dayOverallStatus(_:)` returns a `DotStatus` for the whole day by checking the worst macro deviation. Month: hero stat + 4 weekly adherence dots (W1–W4, colored green/yellow/red by weekly adherence using same thresholds as year monthly dots) + avg cal/day vs target + trend arrow (vs previous 28 days) + best streak. Year: hero stat + 12 monthly adherence dots + best streak. No-targets fallback: week shows logged-day dots, month shows 4 weekly dots (accent/gray), year shows monthly dots + avg cal/day + days logged. All calculation logic lives in `PerformanceCalculator` struct; view code is pure rendering. `PerformanceInfoView` (in `PerformanceInfoView.swift`) explains dot colors, weekly matrix, and stats. Uses `MacroType`, `DotStatus`, `DayRecord`, `PerformancePeriod`, `MacroBarEntry` enums/structs (defined in `PerformanceTileView.swift`); `TrendDirection`, `PerformanceThresholds` defined in `PerformanceCalculator.swift`.
- **User preferences** stored via App Group `UserDefaults` (daily targets, sort order, HealthKit sync toggle, appearance mode) and `UserDefaults.standard` (vision provider selection, OFF device UUID) and Keychain (API keys for vision providers, USDA, and OFF credentials). Keychain items use `kSecAttrAccessibleWhenUnlockedThisDeviceOnly` to prevent iCloud sync.

## Building

Open `FoodTracker.xcodeproj` in Xcode and build for iOS Simulator or device. Camera features require a physical device. The app requires `NSCameraUsageDescription` (set in Info.plist or Xcode target settings).

**Widget setup:** After opening the project, select both the FoodTracker and FoodTrackerWidgetExtension targets, go to Signing & Capabilities, and add the App Groups capability with identifier `group.com.DNT.foodtracker`.

**HealthKit setup:** On the FoodTracker target, go to Signing & Capabilities, add the HealthKit capability. The app requests write access to dietary energy, protein, carbohydrates, and total fat.
